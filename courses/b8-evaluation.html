Part 0

Why evaluation is the whole game

Every algorithm in this track claims to recommend well. Evaluation is how you stop guessing and start measuring. A recommender outputs a ranked list, so its metrics are ranking metrics: did the good items land near the top? Tonight we implement precision@k, recall@k, NDCG, and MAP by hand - no library magic - so you know exactly what each number means, then add guardrails so a model that is accurate but repetitive does not slip through. The honest punchline: offline metrics narrow the field, but only an online A/B test on real users tells you the truth.

Part 1 · covers the evaluation canon

The ranking metrics, defined 6 min live

You hold out a set of items you know the user actually liked (the relevant set), the model produces a ranked list, and every metric asks a slightly different question about how the two overlap. Here are the four that matter, plain.

LivePrecision, recall, NDCG, MAP - each in one line4 min▶
MetricThe question it asksWhen you reach for it
Precision@kOf the top k I showed, what fraction were relevant?Screen real estate is scarce - the top slots must earn their place
Recall@kOf all relevant items, what fraction did I surface in the top k?Coverage of what the user wanted - candidate generation
NDCG@kPrecision, but rewards putting relevant items higherRank order matters, not just presence
MAPAverage precision across users - one number for the systemComparing whole models head to head

Precision and recall are the pair; NDCG adds position sensitivity (a hit at rank 1 is worth more than a hit at rank 5); MAP rolls per-user average precision into a single leaderboard number.

LiveGuardrails: coverage and diversity3 min▶

Accuracy alone is a trap. A model can score well on precision by recommending the same few safe items to everyone - and quietly build a filter bubble. Two guardrails keep it honest:

  • Coverage - what fraction of the whole catalog ever gets recommended? Low coverage means most items are invisible, starving the long tail.
  • Diversity - within one user's list, how different are the items from each other? All-yoga-gear is accurate but narrow; a little breadth aids discovery.
Report accuracy and guardrails together The honest scorecard is never a single number. Precision@k next to coverage and diversity is what stops you from shipping a technically-accurate recommender that shows everyone the same bestsellers - the popularity trap you have been beating since b1.
Part 2 · the split that avoids leakage

Split by time, never at random 4 min live

In most machine learning you shuffle and split randomly. For recommenders that is a bug. A random split can put a user's future purchase in the training set and their past in the test set - the model peeks at the answer. You must split by time: train on the past, test on the future, exactly as production will run.

LiveWhy random splitting leaks - and what to do2 min▶
  • The leak: recommendation is inherently temporal - you predict what a user does next. A random split scrambles time, letting tomorrow inform yesterday. Your offline score inflates and never survives contact with real traffic.
  • The fix: pick a cutoff timestamp. Everything before it is training; everything after is the held-out relevant set. Each user's earlier interactions train; their later interactions are what you try to predict.
  • The reward: the offline number now means something - it estimates how the model would have done on the future it never saw. That is the only offline signal worth trusting before an A/B test.
Real world

The classic false win. A team reports a stellar offline precision, ships it, and the A/B test is flat or negative. Nine times out of ten the culprit is a random split leaking the future into training. Time-based splitting is the single most important habit that makes offline evaluation trustworthy.

Implement the metrics from scratch ★ 12 min · everyone builds

Write precision@k, recall@k, and NDCG@k yourself on a ranked list versus a relevant set - the same YOU-versus-RELEVANT idea the b3 live recommender scored. No library; just the definitions, so the numbers are never a mystery.

Represent a recommendation as an ordered list of item ids, and the truth as a set of relevant items.

Precision@k = hits in the top k / k. Recall@k = hits in the top k / total relevant.

NDCG@k = your list's discounted gain / the best possible discounted gain - it rewards ranking hits higher.

★ Run it now (Python) - precision@k, recall@k, NDCG@k from scratchimport numpy as np # a ranked recommendation list vs the set the user actually liked (held out) ranked = ["Yoga Mat", "Blender", "Yoga Block", "Cookbook", "Foam Roller"] relevant = {"Yoga Mat", "Yoga Block", "Foam Roller"} # ground truth def precision_at_k(ranked, relevant, k): topk = ranked[:k] hits = sum(1 for it in topk if it in relevant) return hits / k def recall_at_k(ranked, relevant, k): topk = ranked[:k] hits = sum(1 for it in topk if it in relevant) return hits / len(relevant) def ndcg_at_k(ranked, relevant, k): # DCG: 1/log2(rank+1) for each hit; IDCG: the best achievable ordering dcg = sum(1.0 / np.log2(i + 2) for i, it in enumerate(ranked[:k]) if it in relevant) ideal_hits = min(len(relevant), k) idcg = sum(1.0 / np.log2(i + 2) for i in range(ideal_hits)) return dcg / idcg if idcg > 0 else 0.0 for k in (3, 5): print(f"k={k}: precision {precision_at_k(ranked, relevant, k):.2f} " f"recall {recall_at_k(ranked, relevant, k):.2f} " f"ndcg {ndcg_at_k(ranked, relevant, k):.2f}")
Read the precision@3 Top 3 here are Yoga Mat, Blender, Yoga Block - two of three are relevant, so precision@3 = 0.67. That is the exact quantity the b3 live recommender's meter animated: popularity landed 0%, and a personalized recommender for a fitness shopper climbed toward 100%. You just implemented the meter.
Demo 2 of 2

Time-split Kirana: personalized beats popularity ★ 10 min · build your own

Now the head-to-head. Split Kirana's interactions by time, train two recommenders on the past - the popularity baseline from b1 and a simple personalized one - and score both on each user's future purchases. Personalization should win on precision@k, which is the whole reason the course exists.

Take timestamped Kirana interactions and cut at a timestamp: earlier = train, later = the held-out relevant set.

Build two recommenders on the training slice: popularity (top sellers) and a co-occurrence personalized one.

Score each user's top-k against their future items and average the precision@k across users.

★ Run it now (Python) - time split + baseline vs personalizedimport pandas as pd from collections import Counter, defaultdict # Kirana interactions with timestamps (day index) df = pd.DataFrame({ "user": ["u1","u1","u1","u2","u2","u2","u3","u3","u3","u1","u2","u3"], "item": ["Yoga Mat","Protein","Blender","Yoga Mat","Yoga Block","Cookbook", "Blender","Cookbook","Whisk","Yoga Block","Protein","Blender"], "day": [1,1,2,1,2,2,1,1,2,3,3,3], }) CUT = 3 train = df[df.day < CUT] test = df[df.day >= CUT] # the future = relevant set future = test.groupby("user")["item"].apply(set).to_dict() # --- popularity baseline: same list for everyone --- pop = [it for it, _ in Counter(train.item).most_common()] # --- personalized: items co-bought with what a user bought in train --- co = defaultdict(Counter) for _, g in train.groupby("user"): its = list(g.item) for a in its: for b in its: if a != b: co[a][b] += 1 def personalized(user, k=2): seen = set(train[train.user == user].item) scores = Counter() for it in seen: scores.update(co[it]) ranked = [it for it, _ in scores.most_common() if it not in seen] return ranked[:k] def precision_at_k(recs, relevant, k): if not relevant: return None return sum(1 for it in recs[:k] if it in relevant) / k def mean_p(recommender, k=2): vals = [] for u, rel in future.items(): recs = pop[:k] if recommender == "pop" else personalized(u, k) p = precision_at_k(recs, rel, k) if p is not None: vals.append(p) return sum(vals) / len(vals) if vals else 0.0 print(f"popularity precision@2: {mean_p('pop'):.2f}") print(f"personalized precision@2: {mean_p('personal'):.2f}") print("# time split (train day<3, test day>=3) - personalization should win")
Real world

Offline picks, online proves. This is the offline test that earns a model its A/B slot: if it cannot beat popularity on a clean time split, it does not deserve live traffic. But even a winning offline number is a hypothesis - real users, novelty effects, and business context can flip it. That is why b9 and b10 wire up online measurement and monitoring, not just this leaderboard.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Your top 3 recommendations contain 2 relevant items. What is precision@3?

Precision@k = hits in the top k / k = 2/3 = 0.67. This is exactly the number the b3 live recommender's meter animated as you switched algorithms.

2 · Why must recsys use a time-based train/test split, not a random one?

Recommendation predicts what a user does next, so shuffling time lets tomorrow inform yesterday. Split at a cutoff: past trains, future is the held-out relevant set.

3 · A model has great precision@k. Is that enough to ship it?

Offline accuracy is a filter, not a verdict. Report guardrails so you do not ship a filter bubble, and let the online A/B test on real users decide the truth.
