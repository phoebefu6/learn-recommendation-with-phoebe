Part 0

Why item-to-item, and why it scaled the web

Early recommenders compared users to users - but with tens of millions of users, that is slow and thrashes as people change. Amazon's insight in 2003 was to flip it: compare items to items. There are fewer items than users, item relationships are stable, and the expensive similarity computation can be done offline, leaving a fast lookup at request time. That is why "customers who bought this also bought" could run on every product page on the planet.

Part 1 · covers Amazon item-to-item CF (Linden, Smith & York 2003)

Items that go together 6 min live

Two items are "similar" if the same shoppers tend to buy both. Represent each item as its column in the interactions matrix - the set of users who bought it - and measure similarity with cosine. Then to recommend for a shopper, take the items they bought and surface the items most similar to those.

LiveCosine similarity, and why offline precompute is the trick3 min▶

Cosine similarity between two item columns is the count of users who bought both, normalized by how popular each is - so it rewards genuine co-purchase, not just popularity. The key engineering move is when you compute it:

  • Offline (batch): compute the full item-item similarity table on a schedule. Expensive, but done away from the user.
  • At request time: for the shopper's items, look up the top-similar items and combine. Fast - a few lookups, no model run.
  • Why it beat user-user: items are fewer and more stable than users, so the precomputed table stays valid longer and is smaller to store.

Real world

Amazon, 2003 (Linden, Smith & York). The paper "Amazon.com Recommendations: Item-to-Item Collaborative Filtering" (IEEE Internet Computing 7(1):76-80) described exactly this - and in 2017 IEEE gave it the Test-of-Time award. The reason it endured: the heavy computation is offline and per-item, so recommendations serve instantly at web scale. You just built its core.

Self-studyCo-occurrence: the "also bought" count2 min read▶

The simplest cousin of cosine is raw co-occurrence: for item X, count how often each other item appears in the same shopper's basket. It powers a literal "customers who bought X also bought Y". Cosine improves on it by dividing out popularity so a mega-seller does not look similar to everything.

★ Run it now (Python) - "also bought" co-occurrence# co-occurrence = how many shoppers bought both X and Y co = mat.T.dot(mat) # items x items counts import numpy as np np.fill_diagonal(co.values, 0) # ignore an item with itself print(co["Yoga Mat"].sort_values(ascending=False).head(3))

Recommend for a shopper with item-item CF ★ 12 min · everyone builds

Turn the item-item similarity table into actual per-shopper recommendations - the function that would sit behind a Kirana product page.

Compute the item-item cosine similarity table from Kirana's matrix (from Part 1).

For a shopper, take the items they bought, pull each item's similar items, and sum the similarity scores.

Remove items they already own and return the top-N by score.

Sanity-check: the recommendations should be things that plausibly go with what they bought - not the store bestsellers.

Compare to the popularity baseline from b1 on the same shopper. Personalization should visibly differ.

★ Run it now (Python) - item-item recommendationsdef recommend_itemitem(user, mat, item_sim, n=3): bought = mat.columns[mat.loc[user] > 0] # sum similarity from each bought item to every other item scores = item_sim[bought].sum(axis=1) scores = scores.drop(index=bought) # do not recommend owned items return scores.sort_values(ascending=False).head(n) print(recommend_itemitem("u1", mat, item_sim))
The offline / online split, in code Notice item_sim is computed once (offline) and reused for every shopper (online). In production that table is refreshed on a schedule (b9) and cached; the per-request work is just the sum-and-sort you see here. That separation is what makes item-item CF fast enough for every page view.

Ship "customers who bought this also bought" ★ 8 min · build your own

The product-page classic: given one item, the items most often bought alongside it. This is item-item CF pointed at a single item instead of a shopper.

Take the item-item similarity (or co-occurrence) table.

For a given product, return its top-N most similar items, excluding itself.

That list is exactly the "customers who bought this also bought" strip. It is content-free - it works from behaviour alone.

★ Run it now (Python) - "also bought" for a productdef also_bought(item, item_sim, n=3): return item_sim[item].drop(index=item).sort_values(ascending=False).head(n) print(also_bought("Yoga Mat", item_sim)) # the product-page strip
Real world

One table, two products. The same precomputed similarity table drives both the personalized shopper recommendations (Demo 1) and the per-product "also bought" strip (Demo 2). That reuse is why item-item CF is such good value: compute similarity once, power several surfaces. In b9 you will decide how often to refresh it and where to cache it.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · In item-item CF, two items are similar when...

Item-item CF is behavioural: similarity comes from co-purchase patterns, not features or price. Category labels are content-based (b5), a different family.

2 · Why did item-to-item scale where user-user did not?

Amazon's 2003 insight: item relationships change slowly and items are fewer than users, so you compute similarity offline and just look it up per request.

3 · In the live recommender, why does popularity score 0% for this shopper?

Popularity ignores the user, so for a fitness shopper it returns the popular kitchen items - none of which are relevant. Personalization is exactly what fixes it.
