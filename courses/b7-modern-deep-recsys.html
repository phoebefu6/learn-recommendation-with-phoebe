Part 0

Where the field goes next

You have built the classic families on Kirana: co-occurrence, item-item and user-user CF, content-based, and matrix factorization. Modern industrial recsys keeps the same goal - fill the blanks in the interactions matrix - but replaces hand-built similarity with learned embeddings and neural scoring. Tonight we map three ideas that dominate production systems: dense embeddings for users and items, the two-tower architecture that generates candidates at web scale, and interest models (Alibaba's DIN and MIND) that rank by paying attention to a user's behaviour. We run tiny sketches to feel the mechanics - not trained models.

Part 1 · learned representations

Embeddings: users and items as vectors 6 min live

Matrix factorization already taught you the core idea: represent each user and each item as a short vector of latent factors, and score a match by their dot product. Deep recsys generalizes this - the vectors (embeddings) are learned, can absorb any feature (category, brand, text, images), and feed neural layers instead of a single dot product.

An embedding table is just a lookup: item id in, dense vector out. Two items that get bought in similar contexts end up with nearby vectors, so nearness in vector space means "recommend-worthy". This is the same geometry you saw in b6, now the shared language of every modern model.

LiveWhy embeddings replaced hand-built similarity3 min▶
  • They fold in side features. A cold-start item with no purchases still has a category and a brand - embed those and it gets a sensible starting vector, softening the cold-start problem from b5.
  • They are trained end to end. Instead of choosing cosine or Jaccard by hand, the model learns the representation that best predicts the outcome you care about (a click, a purchase).
  • They compose. Concatenate a user's embedding with context (time, device) and pass it through layers - the network learns interactions you never coded.
Real world

The same vector, many surfaces. A learned item embedding can power "similar items", search ranking, and the personalized homepage at once - compute it once, reuse everywhere, exactly the offline/online split you saw with item-item CF in b3. That reuse is why big platforms invest so heavily in one good embedding space.

Part 2 · candidate generation at scale

Two-tower retrieval 5 min live

You cannot score every one of a million items with a heavy neural net on every page load. Production systems split the job in two: a fast retrieval step narrows millions of items to a few hundred candidates, then a heavier ranking step orders them. The two-tower model is the standard retrieval design.

LiveWhy two towers, and not one big network3 min▶

The two towers never touch until the final dot product. That separation is the whole trick:

  • Item vectors are precomputed offline for the entire catalog and stored in an index - exactly the offline move from item-item CF, now learned.
  • At request time you run only the user tower once, then find the nearest item vectors with fast approximate nearest-neighbour search. Millions of items, milliseconds of work.
  • Ranking is separate. The few hundred retrieved candidates then go to a heavier model (Part 3) that can afford richer features per candidate.
Retrieve then rank This two-stage shape - cheap recall over everything, then expensive precision over a shortlist - is the backbone of nearly every large recommender. It is also why b8's evaluation separates candidate-generation recall from final ranking quality.
Part 3 · sequence & interest models for ranking

DIN and MIND: paying attention to behaviour 5 min live

A user's history is a sequence - the last twenty things they viewed or bought. Older models averaged that history into one vector, which blurs everything together. Alibaba's Deep Interest Network (DIN, 2018) instead uses attention: when scoring a candidate item, it weights each past behaviour by how relevant it is to that candidate, then sums. A yoga history matters a lot when scoring a mat, barely at all when scoring a blender.

LiveMIND: one user, several interests3 min▶

DIN produces one interest vector per candidate. Alibaba's MIND (Multi-Interest Network with Dynamic Routing, 2019) goes further: it represents a single user with several interest vectors at once, because real shoppers are not one thing.

  • The problem it solves: a user who buys fitness gear and kitchen tools and kids' toys is badly described by one average vector - it lands between all three and matches none well.
  • The move: dynamic routing clusters the behaviour sequence into K interest vectors (fitness, kitchen, toys), and retrieval pulls candidates for each interest separately, then merges.
  • Why it matters for you: multi-interest retrieval directly improves diversity and coverage - the guardrails you will measure in b8 - not just raw accuracy.
Real world

Deployed, published, and cited. DIN (Zhou et al., KDD 2018) and MIND (Li et al., 2019) are Alibaba's published production algorithms for click-through-rate prediction and retrieval, used across its e-commerce platforms including the AliExpress/Lazada family. We are teaching their named cores from the papers - not reproducing Alibaba's full live stack, which is far larger and constantly retrained.

A two-tower scoring sketch ★ 10 min · illustrative only

This is a sketch, not a trained model. We random-initialize a user embedding table and an item embedding table, then score candidates by dot product and take the top-N - exactly the retrieval geometry, with untrained vectors so you can see the mechanics. Real towers learn these vectors from data; here they are random, so the ranking is illustrative.

Make an embedding table for users and one for items - random rows stand in for what a trained tower would output.

Look up one user's vector and every item's vector (the offline item table, in miniature).

Score each item by dot product with the user vector, then return the top-N - the retrieval step.

Demo 2 of 2

An attention-weight sketch (DIN intuition) ★ 8 min · sketch

Again a sketch: we take a candidate item and a short behaviour sequence, measure how similar each past item is to the candidate, and softmax those similarities into attention weights. Relevant history gets more weight - the beating heart of DIN, on toy vectors.

Give the candidate and each past item a small vector (here, fitness-vs-kitchen coordinates - a stand-in for learned embeddings).

Score similarity of each past item to the candidate, then softmax into weights that sum to 1.

Read the weights: fitness history outweighs kitchen history when scoring a fitness candidate.

★ Run it now (Python) - attention over a behaviour sequence (sketch of DIN)import numpy as np def softmax(x): e = np.exp(x - np.max(x)) # stable softmax return e / e.sum() # toy 2-D embeddings: [fitness, kitchen]. A real model LEARNS these. candidate = np.array([1.0, 0.0]) # a fitness item (Yoga Block) history = { "Yoga Mat": np.array([0.95, 0.05]), "Protein": np.array([0.80, 0.10]), "Cookbook": np.array([0.10, 0.90]), "Blender": np.array([0.05, 0.95]), } names = list(history) sims = np.array([candidate @ history[h] for h in names]) # relevance to candidate weights = softmax(sims * 3.0) # sharpen, then normalize for h, w in zip(names, weights): print(f"{h:<10} attention {w:.2f}") # DIN then builds the user's interest as the weighted sum of past-item vectors: interest = sum(w * history[h] for h, w in zip(names, weights)) print("\ninterest vector for this candidate:", np.round(interest, 2)) print("# SKETCH: real DIN learns the attention function; this is the intuition.")
Real world

Why attention beat averaging. Before DIN, models compressed a whole history into one fixed vector, so a diverse shopper looked "average" for every candidate. Attention lets the same history read differently depending on what you are scoring - the fitness past lights up for a mat and stays quiet for a blender. That is the published insight (Zhou et al., 2018); the code above only sketches its shape.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Why does the two-tower model keep the user tower and item tower separate?

The towers meet only at the final dot product. Precomputing the whole item catalog offline lets you run just the user tower per request and find nearest items in milliseconds.

2 · What is DIN's core idea?

DIN weights the behaviour sequence per candidate, so a fitness history counts heavily for a mat and lightly for a blender - instead of blurring everything into one average.

3 · The Demo 1 embeddings are random. What does that mean for its output?

Real towers learn their vectors from millions of interactions. Our random vectors demonstrate dot-product retrieval geometry, but the ranking carries no real signal - it is a sketch.
