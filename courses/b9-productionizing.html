Part 1 · industry serving practice

The two-stage serving pattern 6 min live

You cannot score a million items for every request. So production recsys splits serving into two stages: cheaply retrieve a few hundred plausible candidates, then rank only those with the expensive model. Candidate generation trades precision for speed; ranking trades speed for precision. Together they fit the budget.

LiveWhy two stages, not one3 min▶

Scoring every item with the heavy model per request would blow the latency budget many times over. The split fixes that:

  • Candidate generation (retrieval): a cheap method - co-occurrence lookups, an ANN search over embeddings, or "also bought" from b3 - narrows millions of items to a few hundred in milliseconds.
  • Ranking: the expensive model (matrix factorization from b6, or a deep ranker from b7) now scores only that shortlist, so it can afford rich features.
  • The payoff: the costly model touches hundreds of items, not millions. This is the pattern behind most large-scale recommenders; we teach the shape, not any one firm's internals.
Real world

Retrieve then rank is near-universal. Whether the surface is a streaming homepage or a marketplace product page, the published pattern is the same two stages - a fast retriever proposes, a precise ranker disposes. Kirana does not need billion-item retrieval, but adopting the shape now means the design scales when the catalog does.

Part 2 · batch vs real-time, the feature store, the handoff

Train offline, serve online - and keep them consistent 6 min live

Training is heavy and periodic; serving is light and constant. The art is deciding what to precompute in a nightly batch versus what to score live per request - and making sure a feature means the exact same thing in both places.

LiveBatch precompute vs real-time scoring - when each3 min▶
  • Batch precompute: compute top-N for every user nightly, write to a key-value store, serve by lookup. Cheapest and fastest to serve; recs are as fresh as the last batch. Perfect for stable taste and known users - Kirana's default.
  • Real-time scoring: compute recs per request. Needed for fast-changing context (what you clicked one minute ago), brand-new users, and session-based intent - at the cost of live compute in the latency budget.
  • Common hybrid: batch-retrieve candidates offline, rank live with a few fresh signals. Start batch-only; add real-time only where freshness clearly pays.
Self-studyThe DS to ML-engineering handoff: artifact + contract2 min read▶

The handoff is not "here is my notebook". It is two concrete things:

  • The model artifact: a versioned, serialized model (a pickle, an ONNX file, or a precomputed rec table) plus the exact feature transforms it expects - so serving reproduces training precisely.
  • The contract: the API shape both sides agree on - the request (a user id), the response schema (a ranked list of item ids plus a strategy tag), latency and fallback rules. Freeze it early so the front-end can build against it in parallel.
Train-serve skew is the classic bug If a feature is computed one way in the training notebook and another way in the serving code, the live model quietly underperforms its offline scores. A shared feature store - one definition consumed by both - is the standard fix.
Part 3 · where recs earn money

The engineering UI revamp - surfacing the recs 4 min live

The model outputs a ranked list. Value appears only when the front-end renders it where shoppers look. This is engineering's job, and it is not an afterthought: the same recs in a prominent "Because you bought X" rail versus buried below the fold produce wildly different revenue.

LiveWhere recs get surfaced across the app3 min▶
  • Home page rails: ranked slots like "Recommended for you" and "Because you bought Yoga Mat" - the personalized shelf the ranking model fills.
  • Product page (PDP): "Customers who bought this also bought" - the item-item strip from b3, right under the buy button.
  • Cart and checkout: complementary cross-sell - "add a Water Bottle with those Dumbbells" - the highest-intent moment in the funnel.
Real world

A great model with a bad UI ships no value. Netflix has described the homepage as almost entirely made of personalized rows - the recommendations are the interface, not a widget bolted on (Netflix TechBlog). The lesson for Kirana: design the rail slots and their copy alongside the model, and A/B test placement, not just the algorithm. Two teams, one surface.

Demo 1 of 2

Precompute recs and serve by lookup ★ 12 min · everyone builds

The batch pattern in code: compute top-N for every user once, write them to a key-value store (a dict standing in for Redis), then serve any user with an O(1) lookup - no model runs at request time.

Build Kirana's matrix, then define a simple per-user recommender (any model from b3 to b7 slots in here).

Loop over every user once and write their top-N into a dict - this is the nightly batch job.

Serve with a plain dictionary lookup, falling back to popularity for unknown users. That is the whole online cost.

★ Run it now (Python) - batch precompute + O(1) serveimport pandas as pd, json # Kirana transactions -> implicit users x items matrix tx = pd.DataFrame({ "user": ["u1","u1","u2","u2","u3","u3","u3"], "item": ["Yoga Mat","Protein","Yoga Mat","Dumbbells", "Blender","Cookbook","Yoga Mat"], }) mat = (tx.assign(v=1) .pivot_table(index="user", columns="item", values="v", aggfunc="sum", fill_value=0) > 0).astype(int) POPULAR = mat.sum(axis=0).sort_values(ascending=False).index.tolist() def top_n(user, n=3): # any model from b3-b7 plugs in here owned = set(mat.columns[mat.loc[user] > 0]) return [it for it in POPULAR if it not in owned][:n] # --- OFFLINE batch job: compute once for every user, write to the store --- REC_STORE = {u: top_n(u) for u in mat.index} json.dump(REC_STORE, open("recs.json", "w")) # a dict stands in for Redis print(REC_STORE) # --- ONLINE serve: O(1) lookup, no model runs at request time --- def serve(user, n=3): return REC_STORE.get(user, POPULAR[:n]) # unknown user -> popularity print(serve("u1"), serve("new_visitor"))
Precompute makes serving trivial All the intelligence ran offline; serving is a dictionary get. This is why batch is the default first move - it is nearly free to serve and impossible to time out. Swap top_n for your best model from b6/b7 and nothing downstream changes.
Demo 2 of 2

The API contract, and the front-end that renders it ★ 10 min · build your own

The endpoint is the contract between data and engineering: the front-end sends a user id and gets back a ranked list. Freeze this shape early so both teams build in parallel. Then engineering renders that list as the rec rail.

Wrap the precomputed store in a FastAPI endpoint that returns recs as JSON with a strategy tag.

Agree the response schema - it is the contract; the front-end depends on these exact keys.

On the front-end, fetch the contract and render the "Because you bought X" rail on home, PDP, and cart.

★ Run it now (Python) - the recs API (the contract)# api.py - run: uvicorn api:app --reload from fastapi import FastAPI import json app = FastAPI() REC_STORE = json.load(open("recs.json")) # batch output from Demo 1 POPULAR = ["Yoga Mat", "Protein", "Dumbbells"] # cold-start fallback @app.get("/recs/{user}") def get_recs(user: str, n: int = 3): recs = REC_STORE.get(user, POPULAR)[:n] # the response schema IS the contract the front-end depends on: return {"user": user, "recs": recs, "strategy": "batch-v1"} # GET /recs/u1 -> {"user":"u1","recs":["Dumbbells","Blender","Cookbook"], # "strategy":"batch-v1"}
★ The front-end (engineering builds this) - render the rec rail// FRONT-END - fetch the contract above, paint the "Because you bought X" rail. // The model is worthless until this code puts it on the page. async function renderRecRail(user) { const res = await fetch(`/recs/${user}`); const data = await res.json(); // { user, recs, strategy } const rail = document.querySelector("#home-rail"); rail.innerHTML = `<h3>Because you bought Yoga Mat</h3>` + data.recs.map(name => `<article class="rec-card">${name}</article>`).join(""); } // home page, product page, and cart each mount a rail like this one. renderRecRail("u1");
Real world

The contract lets teams move in parallel. Once the response schema is frozen, the front-end builds the rail against a stub while the data scientist keeps improving the model behind the same endpoint - swapping batch-v1 for rank-v2 without the UI changing a line. That decoupling is the whole point of shipping a contract, not a notebook.

Three questions before you go 🎯 ◐ 90 seconds

1 · Why do production recommenders serve in two stages?

Candidate generation trades precision for speed; ranking trades speed for precision. The costly model touches hundreds of items, not millions.

2 · When is batch precompute the right serving choice?

Batch is nearly free to serve and cannot time out. Reach for real-time only where freshness (fast-changing context, brand-new users) clearly pays.

The artifact reproduces training exactly (a shared feature store prevents train-serve skew); the contract lets the front-end build in parallel against a frozen schema.
